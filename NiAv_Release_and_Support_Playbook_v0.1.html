NiAv Release and Support Playbook

Document ID: NIAV-RSP · Version: v0.6 · Status: Draft / Living · Last updated: 30 Sep 2026

Purpose: Define zero-cost APK issuance, licence-key handling, installation/update workflow, backup/recovery, support triage and incident drills.

This document is part of the NiAv living-document chain. Source changes, verified facts, owner decisions and implementation incidents must be reflected through explicit versioned updates; unresolved TBD/VERIFY items are not silently converted into final rules.

2. Release model

  • V1 is a standalone Android APK distributed by WhatsApp/email under the ₹0 strategy.
  • No paid server is a prerequisite; the offline core must continue if an external free service disappears.
  • Release artifacts include APK, version/change notes, checksum/hash, install instructions and rollback/recovery guidance.
  • Licence issuance remains offline-verifiable; external/manual payment is a user-mediated workflow if adopted.

3. Key issuance workflow

Customer/company identity
        ↓
Edition + term + entitlement matrix
        ↓
Payment evidence (if applicable)
        ↓
Issuer generates signed licence
        ↓
Customer receives key/file
        ↓
App imports/verifies signature
        ↓
Entitlement state stored locally

Never place private signing material inside the APK. Exact licence fields/edition boundaries remain controlled by SEC/ZCP open decisions.

4. Installation guide

  1. Receive APK from the controlled distribution channel.
  2. Verify version and checksum/hash where provided.
  3. Install/upgrade using Android's user-confirmed package installation.
  4. Open NiAv and verify company/DB availability.
  5. Before a major upgrade, take a fresh protected backup.
  6. Verify licence/trial state.
  7. Run a smoke test: create/hold bill, search item, open report, confirm backup status.

5. Update flow

StepActionFailure recovery
1Publish APK + release notes + checksumDo not distribute if artifact integrity is uncertain.
2Customer backs upRestore/verify backup before proceeding.
3Install new APK over supported existing installationStop and preserve old backup if migration fails.
4Run DB migrationsMigration is transactional/recoverable per DB spec.
5Smoke/regression checksUninstall the current APK, install the previous APK, then restore the external backup; in-place downgrade is not supported.

6. Support triage

PriorityExamplesResponse
P0Data loss/corruption, security compromise, broken restore, widespread posting errorStop affected operation; preserve evidence; recover from backup; owner-led incident.
P1Core billing/accounting blocked for one or more usersCollect logs/diagnostics, reproduce with synthetic fixture, issue workaround/release decision.
P2Non-critical defect or report/UI issueCapture steps/screenshots/version; schedule fix.
P3Enhancement/questionDocument request; no emergency change.

7. Incident drill

  1. Identify affected company/app/schema version.
  2. Freeze risky operations if integrity is uncertain.
  3. Preserve backup, audit and diagnostic evidence.
  4. Determine whether issue is data, migration, licence, sync, security or UI.
  5. Restore a copy into a test environment and reproduce.
  6. Apply the smallest safe workaround; never edit production financial records silently.
  7. Verify reconciliation and user-visible result.
  8. Record root cause, affected versions and required document updates.

8. Sync incident

  • If peer trust is suspect, revoke the peer and stop sync.
  • Do not delete the operation log to hide a conflict.
  • Use the conflicts queue and audit history for concurrent edits.
  • If host is lost, restore latest backup on a replacement device and re-pair clients.

Incident, pilot feedback or verified external change → FGA/open item → affected FR/FDD/UX/DB/SYNC → TEST update → release decision → change log. No incident fix should silently change a source requirement.
