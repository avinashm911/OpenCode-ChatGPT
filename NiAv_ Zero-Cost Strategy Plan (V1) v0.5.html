1. Zero-cost rules (the "₹0 gate")

A tool, service, or activity is allowed in V1 only if all of these hold:

  1. No payment now or later: no card/UPI mandate, no "free trial then charge", no auto-renewal.
  2. No usage-based billing risk: a service that bills for overage is barred unless it can be hard-capped at zero.
  3. Licence permits your use: open-source or free licence that allows commercial distribution of an app [VERIFY per component].
    Resolved: Decide before go-live (Decided: owner value)
  4. No dependency on a paid account of yours (e.g., a paid developer programme, paid domain, paid SMS/WhatsApp API).
  5. Removable: if a free tier ends, V1 must keep working (offline core), even if a nice-to-have stops.

Rule of thumb: if a setup screen asks for a card, stop and record it in the decision register.

What "zero cost" does and doesn't cover

  • Covered: software, tools, libraries, hosting/distribution, testing, licensing mechanism.
  • Assumed already owned (A-01): a computer, an Android phone for testing, and an internet connection. Your own time is not counted as a cost.
  • Not in the ₹0 budget: anything requiring new hardware or paid third parties. Listed under "Deferred" in Section 5.

2A. Integration levels: file-first, API-second

₹0 V1 must not treat "API unavailable" as equivalent to "integration impossible". Each external workflow is classified separately:

  • Level 0: local calculation/validation.
  • Level 1: JSON/CSV/XML/Excel/PDF export.
  • Level 2: user-mediated upload/submission through the external portal/app.
  • Level 3: import of acknowledgement/error/result files and local reconciliation.
  • Level 4: Android/device integration such as share sheet, filesystem, Bluetooth, camera and LAN.
  • Level 5: direct API integration; deferred unless it can remain within the ₹0 rules and required credentials/registrations are acceptable.

Design rule: prefer Levels 0–4 for V1. API automation is an optimization layer, not a prerequisite for the underlying business workflow.

3. Architecture strategy

Principle: one self-contained Android app. No backend.

[Android APK]
  ├─ UI layer (screens, language packs, customisable layouts)
  ├─ Domain layer (voucher engine, numbering, document flow, approvals, GST calc)
  ├─ Data layer (local SQLite database, search index, attachments folder)
  ├─ Import/Export (Excel templates, PDF, backup files)
  └─ Licence & trial module (offline signature check)
  • Database: SQLite on device (free, public domain). Single company database file per company, which makes backup/restore and transfer simple.
  • Search: indexed local search (SQLite full-text index if the bundled SQLite build supports it [VERIFY], otherwise an in-memory index built at app start).
  • No network permission required for the core app. Network is used only for optional features like sharing via other apps. This also reduces privacy exposure.
  • Accounting integrity: double-entry postings generated by the voucher engine, with stock movements derived from inventory lines. All logic is local and unit-testable.

6. Multi-user strategy: offline-first with LAN/hotspot sync (D-02 resolved)

Correction to v0.1: multi-user, multi-device is possible at ₹0 by syncing directly between phones on the same Wi-Fi or a phone hotspot, with no internet or server. "Online" here means "connected to the shop network". Sync across different locations over the internet needs a relay/server, which I cannot guarantee at ₹0, so that is deferred.

6.1 Topology

 [Host device: owner's phone/tablet]  ◄── LAN / hotspot ──►  [Counter 1]  [Counter 2]  [Godown phone]
   authoritative company DB + sync service                   each has a local replica, works offline
  • One host per company holds the authoritative database and runs the sync service (foreground service with visible notification).
  • Clients keep a full local replica (V1) and work fully offline; they sync whenever they can reach the host.
  • Host loss or replacement: restore the latest backup on a new device, make it host, re-pair clients.

6.2 Data model for sync (build from day one)

  • Append-only operation log: every change is an operation {op_id, device_id, seq, timestamp, entity, action, payload}. Local tables are a projection of the log.
  • UUID primary keys for all records created offline (parties, items, vouchers). Human-readable codes are separate fields.
  • Voucher numbering with no collisions: each device gets its own series prefix per voucher type (this uses USP 2, multiple series). The host rejects foreign prefixes.
  • Stock and balances are derived from vouchers, so merging vouchers yields consistent totals. Merges can produce negative stock or credit-limit breaches; these show in an exception report.
  • Conflict rules: posted/approved documents are read-only; edits carry a version number; if two devices edit the same record, the host accepts the first arrival, and the second goes to a Conflicts queue for the owner to resolve. Master-data edits use field merge; host arrival wins on a same-field clash and the loser is logged with audit history.
  • Approvals: requests and decisions are operations; the host arbitrates state transitions so one document cannot be approved and rejected at once.
  • Period locks, user rights and series assignments are pushed from the host to clients.

6.3 Transports of the same log (staged delivery)

  1. File transport (fallback, ships first): export/import of operation files by WhatsApp/email/USB. Useful for backups and offline-only sites.
  2. LAN/hotspot transport: direct HTTPS sync with QR pairing (security details in Security Plan Section 6). Both use the same log, so the file path is not wasted work.

6.4 Android realities to test [VERIFY]

Foreground-service and battery-optimisation behaviour on low-end phones; hotspot networks that isolate clients from each other; local-network permission changes across Android versions; QR pairing avoids relying on automatic discovery.

6.5 Risk and gates (be realistic)

Sync is the hardest part of the system for one developer. To control risk:

  • Gate S1: operation log and file transport working with automated merge tests (two simulated devices).
  • Gate S2: LAN sync between two real phones, including offline creation and merge.
  • Gate S3: three devices, conflicts, revocation, and a low-end phone in a hotspot test. If a gate slips, release V1 with the previous gate's capability (file merge or single device) and finish LAN sync in V1.1. Users are told plainly what V1 supports.

6.6 Simple vs Advanced

Proposal: Simple edition = 1 user, 1 device. Advanced = multiple users and devices with sync, approvals and admin controls (see Section 7.3, to confirm).
