2. Schema principles

  • Local SQLite/Drift is the V1 authoritative store.
  • Company scope is explicit and enforceable.
  • Stable IDs are separated from display numbers.
  • Posted/audited history is preserved rather than silently deleted.
  • Derived data can be rebuilt where practical.
  • Operation log, audit and batch records are first-class persistence concepts.

7. Representative indexing strategy

  • Company + voucher date/type/number.
  • Company + party + due date for outstanding.
  • Company + item + godown + batch for stock reads.
  • Barcode/code/alias/name search indexes for item and party lookup.
  • Operation ID, device + sequence and company scope.
  • Import batch + row/field error lookup.
  • Audit entity + entity ID + time.

8. Migration/versioning

  1. Schema version is stored locally.
  2. Each application release declares required migration range.
  3. Migrations are deterministic and tested against representative prior databases.
  4. Before destructive transformation, backup/restore validation is required.
  5. Migration failures leave the source database recoverable; no silent partial schema conversion.

13. Acceptance criteria

  • Every FRD domain requirement has a logical persistence location or is explicitly transient/calculated.
  • Company isolation can be enforced by schema constraints/query policy.
  • Voucher numbering is unique within its defined scope.
  • Import and sync replay can be detected from persisted identifiers.
  • Audit evidence remains queryable and protected.
  • Backup/restore can reconstruct an internally consistent company database.
  • Derived data can be rebuilt from authoritative records for defined fixtures.
