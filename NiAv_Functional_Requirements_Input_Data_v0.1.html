2. Functional requirement conventions

  • Shall: requirement for the stated scope. Conditional fields depend on feature/transaction/edition configuration.
  • TBD / VERIFY: deliberately unresolved; must not be treated as a final implementation rule.
  • Acceptance: each FR eventually needs a test, golden fixture, reconciliation proof or owner-approved UX test.

7. Core validation and correction rules

  • Mandatory-field checks shall block the state transition that requires a complete record.
  • Reference fields shall resolve to valid masters; quick-add is allowed only where the source specifies it.
  • Import validation includes mandatory fields, duplicates, unknown groups/ledgers/items, unit mismatch, GSTIN format, date range and Dr=Cr as specified by M17.6. fileciteturn51file1L1-L1
  • Imported files and sync batches are untrusted input and must pass the security validation path before persistent changes.
  • Posted records shall not be silently rewritten; use permitted alteration/cancellation/reversal and audit mechanisms.
  • Rights and lock rules must be checked at the action boundary, not only by hiding controls.

9. Import / migration requirements

REG explicitly defines versioned Excel templates, bulk masters, opening balances, legacy transactions, Tally/Busy mapping guidance, validation, preview/error reports, create/update/skip modes, import batch logging/rollback and reconciliation. fileciteturn51file1L1-L1

  • Every import identifies template/schema version.
  • Column mapping is explicit and reviewable.
  • Dry-run validation makes no persistent changes.
  • Error reports identify row/field/reason.
  • Import mode is an explicit user choice.
  • Every batch receives a batch ID and, where supported, source fingerprint/hash.
  • Rollback is batch-level where M17.9 is implemented.
  • Post-import trial balance and stock reconciliation is required before migration sign-off.

10. Statutory / file-first requirements

ZCP defines GST calculation/reporting and Excel/JSON export and covers GST return JSON in R1a; e-invoice/e-way are R3/G3; TDS/TCS later release; PF/ESI/payroll out of scope via local export, user-mediated submission and response import when formats are verified; direct APIs remain separate/deferred. fileciteturn48file5L1-L1

  1. Collect source accounting/party/tax/transport data locally.
  2. Validate against a versioned, verified adapter.
  3. Generate the file/payload.
  4. User submits externally where required.
  5. Import response/result and link it to the originating record.
  6. Reconcile and retain the audit trail.

Exact statutory fields, applicability and current official schemas remain VERIFY until evidenced in the source verification logs.

12. Security and untrusted input

SEC states that client-only offline software cannot be made unbreakable and uses defense-in-depth, protected data, secure sync, recovery and audit controls. fileciteturn47file1L127-L128

  • Never trust imported files or sync peers solely because of their transport.
  • Validate structure and business semantics before commit.
  • Protect credentials/secrets and do not store them as ordinary plaintext fields.
  • Record actor/time/device and old/new values for auditable changes.
  • Apply authenticated/encrypted mechanisms for backup and sync as specified by SEC.
  • Detect duplicate/replayed import and sync batches.
  • Licence restrictions must not destroy user data.
