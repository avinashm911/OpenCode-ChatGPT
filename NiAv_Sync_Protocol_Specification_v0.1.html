NiAv Sync Protocol Specification

Document ID: NIAV-SYNC · Version: v0.6 · Status: Draft / Living · Last updated: 30 Sep 2026

Purpose: Define the common operation-log protocol for LAN/hotspot sync and user-mediated operation-file exchange, including pairing and conflict rules.

2. Protocol architecture

                     ↓
              operation batch

3. Operation envelope

FieldLogical typePurpose
op_idUUIDGlobally stable operation identity; duplicate/replay key.
device_idUUIDOriginating trusted device.
seqMonotonic integerPer-device operation sequence; gap detection.
timestampUTC timestampCreation/apply evidence; not sole conflict authority.

signature/hashIntegrity metadataAuthenticity/integrity according to SEC design.

4. Transport modes

ModeUseSecurity/behavior
Operation fileWhatsApp/email/USB/user-mediated remote exchangeProtected batch; validate before apply; fingerprint/replay detection.
LAN/hotspot HTTPSPrimary local sync path where Gate S2/S3 is passedTrusted pairing, authenticated peer, host arbitration, visible sync mode.
Backup restoreHost replacement/recoveryNot ordinary sync; explicit restore validation and re-pairing.

5. Pairing protocol

  1. Host enters explicit pairing mode.
  2. Host displays QR/bootstrap data.
  3. Client scans and establishes device identity/key material.
  4. Both sides confirm company identity and pairing intent.
  5. Host records peer as trusted with status and permissions.
  6. Revocation removes trust; future operations from that peer are rejected.

QR pairing is preferred to automatic discovery. Android network/foreground-service behavior remains a VERIFY item.

6. Conflict rules

ScenarioRuleEvidence
Posted/approved document editReject as normal edit; use permitted alteration/reversal path.Preserve audit evidence.
Two devices edit same mutable recordHost accepts first arrival; later operation goes to Conflicts queue.Owner resolves; no silent overwrite.
Master-data concurrent editField-by-field merge; on a same-field clash, host arrival wins and the loser is logged.Record both histories.
Approval raceHost arbitrates state transition.One document cannot become approved and rejected simultaneously.
Duplicate operationRecognize op_id/device+seq and do not apply twice.Idempotent.
Series mismatchHost rejects foreign/unowned voucher series prefix.Prevents numbering collision.

7. Host authority

  • Host rechecks user rights, period locks, series ownership and approval rights at apply time.
  • Host maintains authoritative ordering for accepted operations.
  • Clients may work fully offline and later synchronize.
  • Host loss: restore latest backup, designate new host, re-pair clients.

8. Security controls

  • Device key pairs and mutual authentication where specified by SEC.
  • Only trusted peers may exchange/apply operations.
  • Signed/hashed operations protect integrity; imported files are untrusted until validation.
  • Rate limiting and visible sync-mode activation reduce unwanted exposure.
  • Redaction rules apply to diagnostics/logs.

GateExit criterionPurpose

S2Two real phones over LAN/hotspot including offline creation/mergeDevice/network validation
S3Three devices, conflicts, revocation, low-end phone hotspot testRelease-hardening gate
