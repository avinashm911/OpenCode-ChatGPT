2. UX principles

  • Fast daily billing and accounting entry take priority over decorative UI.
  • English/Hindi/Gujarati and native-script entry are first-class where scoped.
  • Offline state is understandable without blocking local work.
  • Errors are actionable and preserve entered data when safe.
  • Complex import/sync flows use staged review rather than one-tap destructive actions.
  • Rights and edition limits are enforced functionally, not merely by hiding controls.

6. Form specification

  • Every field has label, value state, requiredness and error state.
  • Conditional fields appear only when their enabling condition is true, but their values remain auditable.
  • Primary action text changes with state: Save, Hold, Submit, Approve, Post, Restore, Import, etc.
  • Totals are visible and recalculate deterministically.
  • Long forms use sections/accordions without hiding validation failures.

7. Fast billing UX

  1. Focus item search on entry.
  2. Accept barcode/code/name/alias.
  3. Add item to cart with quantity and price.
  4. Show tax/discount/total summary.
  5. Select payment mode or hold bill.
  6. Finalize and show print/share options.

8. Import/migration UX

Use a six-stage wizard: Select → Map → Validate → Preview → Commit → Reconcile. Invalid rows must be downloadable/viewable as an error report. Commit controls must state the selected mode and whether rollback is available.

9. Approval UX

Show pending state, rule/threshold context, document totals, relevant supporting data and action history. Reject/send-back requires reason where the source rules require it. Approval does not bypass final posting validation.

10. Sync/backup UX

  • Show device/host identity and trust state.
  • Show last sync/backup time and current pending work.
  • For conflicts, show local/remote values and a safe resolution path.
  • For restore, show backup identity, company identity, version and validation status before commit.

11. Localization and accessibility

  • Never hard-code user-visible strings in business logic.
  • Support native-script data and localized labels/errors.
  • Respect Android font scaling and touch accessibility.
  • Use icons with text labels where ambiguity is possible.
  • Do not rely on color alone to communicate state.

14. Acceptance criteria

  • Every FRD input requirement has a discoverable UI entry point or is explicitly system-generated/imported.
  • Every error has a visible, actionable state.
  • Fast billing can be completed with minimal navigation after setup.
  • Import/sync/restore cannot commit without required review/validation.
  • Native-script and localization behavior is testable without changing business logic.
